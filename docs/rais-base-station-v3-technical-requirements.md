**Companion document:** _2026 PIR v3 Technical Requirements.md_ (sensor). Cross-references to sensor requirements use their IDs (RF-x, PWR-x, FW-x).  
**Baseline design:** RAIS2.1 — ESP8266 (Wi-Fi, cloud link, provisioning) \+ CC1312R concentrator (sub-GHz radio), external 902–928 MHz antenna (2.33 dBi), 5 V input via micro-USB-B or barrel, machined enclosure 137×91×24 mm. Cloud link: MQTT (ThingsBoard gateway API) and HTTP to app.retailaware.com over plain `WiFiClient` — **no TLS today**. The ESP8266 can already field-reflash the CC1312 over serial via the TI ROM bootloader, with a server-commanded rollback (`erase_cc1312_firmware`).

Priorities mirror the Base Station v3 product requirements. Where the engineering evidence argues for raising a priority, that is flagged in the rationale rather than silently changed.

## **Appendix A — Implementation Notes & Solution Proposals**

### **A.1 What the RAIS2.1 review established (baseline facts)**

The concentrator is a **CC1312R running the identical PHY to the PIRW2 sensor** — 915 MHz, GFSK, 150 kbaud, ±180 kHz deviation, 621.6 kHz RX BW, same sync word (0x930B51DE) — already configured for \+14 dBm TX (with `CCFG_FORCE_VDDR_HH`). So the base station is _ahead_ of the sensor on TX power today, and the whole "both ends must match" problem reduces to shipping one coordinated firmware pair. The ESP↔CC1312 protocol is line-based serial with `ACK>` framing; the node table (addresses, types, per-node protocol version, settings) is server-managed and pushed to the concentrator, which is exactly the hook RAD-2's per-sensor PHY selection needs.

Two details worth surfacing in the meeting: `RadioProtocol.h` caps `NODERADIO_MAX_TX_POWER` at **13 dBm** — the settings pipeline itself limits sensor TX power, so the sensor-side \+14 dBm change (sensor doc A.1) also touches this shared constant. And `PROTOCOL_VERSION_1` states "nodes are in charge of all collision avoidance" — with v3 sensors synchronizing to a 10 s batch tick (FW-1), many sensors can converge on the same transmit instant; the sensor's CCA plus a per-node random offset within the tick should be specified explicitly (RAD-6).

### **A.2 Ethernet & platform (NET-1..3, PLT-1)**

Two credible architectures: **classic ESP32 \+ LAN8720 PHY** (uses the on-chip EMAC, cheapest BOM, well-trodden Arduino/IDF path) or **any ESP32-family part \+ W5500 SPI Ethernet** (simpler layout, offloads TCP, but a second TCP stack to manage under MQTT/TLS). Recommendation: classic ESP32 \+ LAN8720 unless the RF/PCB team prefers the S3 for other reasons. The migration also retires the three chronic RAIS2.1 pain points visible in the dev notes: SoftwareSerial to the CC1312 (→ hardware UART, and the 57600 baud limit on concentrator reflash can rise, shortening update windows), heap exhaustion around MQTT and JSON buffers (ESP32 has \~4× the RAM; keep the existing heap telemetry), and the deferred SSL work (SEC-1).

Interface arbitration (NET-3): treat Ethernet as primary when link is up and DHCP/static config resolves; fall back to Wi-Fi after a defined timeout; report `active_interface` in the 10-minute attribute update alongside the existing heap/version fields.

### **A.3 TLS & secrets (SEC-1, SEC-2, SEC-4)**

Keep the ThingsBoard gateway API exactly as-is (topics, token auth) and change only the transport: `WiFiClientSecure`/mbedTLS to port 8883, HTTPS for the HTTP endpoints and firmware downloads. The real design work is operational: a CA bundle that survives 5+ years of fleet life (ship 2–3 roots, make the bundle OTA-updatable), and the NTP-before-TLS boot ordering — define explicitly what a base station does when it has network but no time (proposal: retry NTP aggressively, buffer sensor data locally, never skip cert validation as a "temporary" measure). Move token/SSID/password/link keys from raw EEPROM into encrypted NVS (SEC-4); this falls out nearly free on ESP32.

### **A.4 Sub-GHz link encryption & pairing (SEC-3)**

Proposal sketch for the joint sensor/base design: AES-128-CCM using the hardware AES in both the CC1312 and the sensor's radio MCU; a per-site network key delivered to the base station over TLS and to sensors during a pairing procedure (button-initiated join window, or factory pre-provisioning keyed to the QR-code identity — the second fits the existing "server assigns node table" flow better and needs no installer action); 4-byte MIC plus a frame counter for replay protection. Cost on the sensor side is \~8 bytes per packet and microjoules of AES — update the energy model's payload input from 20 to \~28 bytes (the difference is \~1% of battery life; already covered by margin). The frame counter must survive sensor sleep and battery changes (persist to flash on a coarse grain, jump-ahead on boot).

### **A.5 PoE & USB-C (PWR-1..3)**

Average draw roughly doubles vs RAIS2.1's 175 mW (ESP32 \+ PHY \+ TLS crypto bursts), landing near 1.5–2 W worst case — 802.3af **Class 1** (≤3.84 W) with margin. Use an integrated isolated PD module (e.g. Ag99xx/Si34xx class) producing the 5 V rail; diode-OR or ideal-diode controller against the USB-C input, PoE preferred. USB-C needs only the 5.1 kΩ CC pull-downs for 5 V/up-to-3 A sink operation — no PD controller required. Decide the barrel jack's fate in mechanical review; it costs little but the product doc only mandates keeping _USB_ power.

### **A.6 Radio migration & capacity (RAD-1, RAD-2, RAD-6)**

Rollout sequence that never strands a site: (1) push v3 CC1312 firmware (dual-PHY capable) to deployed RAIS2.1 fleet via the existing bootloader path, verified per-site by the version telemetry; (2) deploy v3 sensors, which the node table marks as v3-PHY; (3) legacy PIRW2 sensors continue on the legacy PHY through the transition mode; (4) when a site's fleet is fully migrated, disable legacy listening remotely. Rollback exists at every step (`erase_cc1312_firmware` equivalent must be preserved — PLT-2).

Capacity: at a 10 s upload cycle with `MAX_TELEM_POINTS_PER_UPLOAD_CYCLE = 96`, the current pipeline nominally supports \~96 batched sensor reports per cycle — comfortably above realistic per-store sensor counts, but the ESP8266's 256-byte JSON message limit and heap history say the _buffers_, not the arithmetic, are the risk. Size for a declared max (proposal: 50 sensors/base) with headroom, and add an overflow counter to telemetry so saturation is visible rather than silent.
